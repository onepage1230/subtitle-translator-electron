# ops-review — 審查派工模板

審查程式碼改動的標準流程。核心原則：**審查者必須是 fresh context**（不帶實作過程的記憶），否則會沿用實作時的盲點。

## 步驟

1. **確定範圍**：把要審的東西固定成明確的 diff 範圍（例如 `git diff main...HEAD`、某 commit 區間、或 PR 編號）。範圍寫不出來就先問使用者。

2. **選審查者**：
   - 動到 `electron/main/utils/translate.ts` → 專案 agent `translation-pipeline-reviewer`
   - 其他程式碼 → `general-purpose`，`model: sonnet`
   - 高風險改動（資料遷移、併發、檔案覆寫邏輯）→ 審完再加一份第二意見：`model: opus`，兩份衝突時回報使用者裁決

3. **填派工單**：

   ```text
   【目標與動機】審查：$ARGUMENTS
   這次改動宣稱要達成：＿＿＿（從需求原文抄）
   特別關注：＿＿＿（例如併發安全／glossary 一致性；沒有就寫「無」）
   【驗收條件】
   - 先驗證「宣稱 vs 實際」：改動是否真的做到宣稱的事（必要時實跑測試）
   - 每個發現附 檔案:行號 與嚴重度：blocker（會出錯）/ should（該修）/ nit（風格）
   - 沒有發現也要明說「檢查了 X、Y、Z，未發現問題」，列出檢查面向
   【回報格式】依嚴重度分組列點：`嚴重度 檔案:行號 — 問題一句話 — 建議修法一句話`。
   不貼大段程式碼；引用不超過 3 行。
   ```

4. **收貨檢查**：每個發現都有 檔案:行號 與嚴重度嗎？「未發現問題」有列出檢查面向嗎？缺的退回。

5. **處理發現**：blocker 必修；should 逐條決定（修／開 issue／明說不修的理由）；nit 可批次修或忽略。修完的改動若非 trivial，再走一輪本模板（最多兩輪，之後回報使用者）。

## 注意事項

- 收到審查意見不等於照單全收：技術上站不住的發現要驗證後反駁，附證據（見 `superpowers:receiving-code-review` 的精神，與本制度不衝突）。
- 審查者只審不修；修改回到原做工者或主對話，責任分離。
