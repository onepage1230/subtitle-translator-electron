# 04 — 維護協議（未來 session 如何安全更新制度檔）

本檔規範 `docs/ops/*.md`、`CLAUDE.md`、`.claude/commands/ops-*.md` 的修改方式。任何等級的模型照本檔執行即可，不需要額外判斷。

## 1. 哪些可以自行改、哪些要先問使用者

### 可自行改（改完直接 commit，用 `ops:` 前綴）

- 在對應檔案的「教訓紀錄」區塊**新增**一條 post-mortem（格式見 §2）
- 修正**事實錯誤**：失效的路徑、改名的指令、過時的模型字串——前提是附上查證方式（實際 `ls`／官方文件 URL），寫進 commit message
- 為既有判準**補充範例**（正例/反例），不改判準本身
- `00-inventory.md` 隨環境事實更新（新裝的 skill、新 MCP、agents 變動）
- `10-architecture.md` 跟隨程式碼現況更新

### 要先問使用者（提案 + 理由，等回覆再動）

- 改變**規則語意**：優先序、升降級門檻（幾次失敗才升級）、驗收條件的放寬、Stop Conditions
- 刪除任何檔案或整個章節（新增和修正可以，刪除要問）
- CLAUDE.md 的硬規則區塊，或任何會讓 CLAUDE.md 超過 60 行的改動
- `.claude/settings.json`、`settings.local.json`（本來就是 Stop Condition）
- 新增第六個以上的 `/ops-*` 模板（先確認需求真的不被現有五個涵蓋）

判斷模糊時的預設：**當成「要先問」處理**。

## 2. 踩坑後教訓寫回哪裡、用什麼格式

### 格式（post-mortem 四段，一條約 4–8 行）

```markdown
### <日期> <一句話標題>
- **症狀**：當時觀察到什麼（錯誤訊息、錯的行為）
- **根因**：真正的原因（不是表面現象）
- **修法**：這次怎麼解的（附 commit hash 或 檔案:行號）
- **通則**：下次遇到同類情況的一般性規則
```

### 寫回哪個檔（按教訓性質分流）

| 教訓性質 | 寫到哪 |
|---|---|
| 派工/收貨/驗收流程的坑（派錯 agent、回報格式失效） | `02-delegation.md` 末尾「## 教訓紀錄」 |
| 判斷失誤（該停沒停、該升級沒升級、誤觸發 skill） | `03-judgment.md` 末尾「## 教訓紀錄」，且把通則升格成對應小節的新判準（附正反例） |
| 環境事實變動造成的坑（工具改版、路徑變了） | 直接修正 `00-inventory.md` 正文，不用教訓區 |
| 本專案程式碼的坑（pipeline 行為、打包） | `10-architecture.md` 相關段落，或依既有慣例寫入 auto-memory（跨 session 的個人記憶） |
| 跨專案通用的坑（工具鏈、pnpm 之類） | auto-memory（`~/.claude/projects/.../memory/`），不放本 repo |

檔案還沒有「## 教訓紀錄」區塊就建一個（放檔案最末尾）。

## 3. 精簡門檻

- 任何單一制度檔超過 **150 行**，或「教訓紀錄」超過 **5 條** → 執行精簡：把重複的合併、把已升格為正文判準的教訓刪掉原始條目、把過時的移除。
- 精簡屬於「刪除章節」→ 按 §1 要先問使用者，提案時附「刪什麼、為什麼、保留什麼」清單。
- CLAUDE.md 永遠 ≤ 60 行：要加新路由就同時找一行可刪的，加不進去代表該路由不夠重要。

## 4. Commit 慣例與追蹤

- 制度檔（`docs/ops/`、`CLAUDE.md`、`.claude/commands/ops-*`）的 commit 一律用 **`ops:`** 前綴，一句話說明（例：`ops: 03 新增誤觸發 tdd 的教訓與判準`）。
- 制度演變用 `git log --oneline -- docs/ops/ CLAUDE.md .claude/commands/` 追蹤；接手中斷的 ops 工作先跑這條。
- 一次 commit 只改一個主題；教訓紀錄與規則修正分開 commit。

## 5. 驗證義務（改制度檔也要驗）

改完任何制度檔，最低驗證：

1. 檔內引用的每個路徑、指令、skill 名實際存在（`ls`、`git ls-files` 驗）
2. 與其他制度檔沒有矛盾（grep 相關關鍵詞，交叉讀對應段落）
3. 語意改動（若經使用者同意）：派一個 fresh-context subagent read-back，確認弱模型讀起來無歧義
