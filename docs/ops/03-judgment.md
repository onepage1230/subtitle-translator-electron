# 03 — 判斷力外化（rubric 與 checklist）

把「需要判斷」的決策寫成可機械執行的規則。用法：遇到猶豫時，找到對應小節，逐條核對，**符合條件就執行對應動作，不要再自行權衡**。每條判準附正例（✅ 該這樣）與反例（❌ 不該這樣）。

## 1. 何時該換更強的模型

符合任一條就升級（路徑照 `02-delegation.md` §5）：

- [ ] 同一子任務已失敗（驗收未過）達到門檻：Haiku 一次、Sonnet 兩次
- [ ] 錯誤訊息每次都不一樣，且你說不出「下一次要改什麼」——代表不是手誤是理解不足
- [ ] 任務需要跨 3 個以上模組同時推理（例：改 `pipeline.ts` 的併發邏輯要同時顧 `translate.ts` 重試與 `subtitle.ts` 原子寫入）
- [ ] 高風險判斷需要第二意見（`02-delegation.md` §6 表格第三列）

**✅ 正例**：Sonnet 修 chunk 對齊 bug，第一次改完測試仍紅、第二次改另一處還是紅。→ 停手，整理兩次的 diff、測試輸出、已排除假設，升 Opus。
**❌ 反例**：Sonnet 第一次測試沒過，立刻升 Opus「保險起見」。→ 錯。一次失敗屬正常迭代，帶著錯誤訊息自己再修一次。
**❌ 反例**：連錯兩次後不升級，換個寫法再試第三、四次。→ 錯。這是在燒 token 重走死路。

## 2. 何時算真的完成

全部勾完才能說「完成」；缺一項就只能說「改好了但尚未驗證 X」：

- [ ] 驗收條件逐條對過（派工單或使用者原話裡的每一條，不是你記得的版本）
- [ ] 程式碼改動：`npm test` 實際跑過且輸出貼得出來；動到 UI 的加跑 E2E
- [ ] 新檔案／文件：fresh-context read-back 驗過（`02-delegation.md` §6）
- [ ] 沒有「順手改了但沒講」的改動——`git diff --stat` 裡每個檔案都能對應到任務
- [ ] 使用者原話裡的**每個子句**都處理了（「修好 A 並確認 B 不受影響」是兩件事）

**✅ 正例**：「tsc 過了、`npm test` 42 個測試全綠（輸出如下）、read-back 確認文件三個需求都有對應段落。完成。」
**❌ 反例**：「型別檢查過了，應該沒問題，完成。」→ tsc 過只代表型別對，不代表行為對；「應該」是未驗證的同義詞。

## 3. 何時該停下來問使用者

符合任一條**立刻停**，把選項與你的建議整理好再問（一次問完，不要擠牙膏）：

- [ ] 動作不可逆或影響範圍出了 repo：刪檔、git 破壞性操作、加依賴、改 `.claude/settings.json`、動 `.env` 或含金鑰檔案（本環境 Stop Conditions 原文）
- [ ] 兩個合理方案會導致**不同的使用者可見行為**，且需求原文判不出要哪個
- [ ] 發現任務的前提有誤（例：使用者說「修 X 的 bug」，但 X 的行為其實是刻意設計，有 ADR 佐證）
- [ ] 完成任務必須越出原始範圍（例：修 bug 發現得先升級依賴才修得掉）

**✅ 正例**：「重試機制有兩種改法：A 保持 5 次上限但加 jitter（行為不變）、B 改成無上限直到逾時（使用者會等更久）。我建議 A，因為……你要哪個？」
**❌ 反例**：測試檔某個 import 路徑有兩種寫法、專案裡兩種都有人用。→ 不要問。挑與鄰近檔案一致的那種，在回報裡提一句即可。
**❌ 反例**：每做完一小步就問「可以繼續嗎？」→ 不要問。反例判準：如果答案顯然是「可以」，就不要問。

## 4. 什麼訊號代表方向錯了（該換路，而非重試）

重試 = 同一方法再來一次；換路 = 承認假設錯了。出現任一訊號就**禁止原地重試**：

- [ ] 修好 A 弄壞 B、修好 B 又弄壞 A（蹺蹺板）——代表兩者共享的抽象層才是問題
- [ ] 為了讓方案能動，需要的「例外處理」越加越多（第三個 special case 出現時就是訊號）
- [ ] 你開始想改測試來遷就實作，而不是相反
- [ ] 同樣的錯誤訊息在兩次不同的修法後原樣出現——你改的地方根本不在因果鏈上
- [ ] 方案依賴一個你沒驗證過的假設，而驗證它只要一分鐘（先去驗！）

換路的動作：停手 → 寫下目前假設與反證 → 回到上一個確定正確的狀態（git）→ 提出新假設或升級模型（帶軌跡）。

**✅ 正例**：修 glossary 過濾漏詞，加了連字號變體匹配後又發現大小寫變體、再發現全形字元變體。第三個變體出現 → 停手，換路：問題不是「再加一種變體」，是匹配該先做正規化。
**❌ 反例**：同一個 `generateObject` schema 錯誤，換三種 prompt 措辭重試。→ 錯訊息沒變就是方向沒變，該去看 schema 定義本身。

## 5. 品質底線怎麼驗

「能跑」不是底線，以下是每種產出的最低驗法（做的人先自查，驗收者再照 `02-delegation.md` §6 獨立驗一次）：

| 產出 | 底線驗法 |
|---|---|
| 程式碼改動 | `npm test` 綠 + 針對改動寫的至少一個新測試也綠（沒有新測試 = 這次改動沒有回歸保護，要在回報裡明說） |
| 翻譯 pipeline 相關（`electron/main/utils/`） | 上一條 + 用 `tests/unit/` 現有 fixture 實跑一次相關函式；動到 `translate.ts` 的必過 `translation-pipeline-reviewer` |
| UI 改動 | `npm run pree2e && npm run e2e`；沒有對應 E2E 的頁面，先派 `e2e-writer` 補 |
| 文件 | read-back：驗收者不看摘要、只比對「需求清單 vs 檔案內容」；所有引用的路徑/指令實際存在（`ls` / `which` 驗） |
| 制度檔（docs/ops/） | 上一條 + 檢查與其他制度檔無矛盾（grep 相關關鍵詞交叉讀） |

**✅ 正例**：改了 `filterGlossaryForText`，補一個「連字號變體」的測試案例，跑全套測試綠，才送審。
**❌ 反例**：文件裡寫「用 `/ops-verify` 模板」但那個 command 根本不存在（`/ops-verify` 正是不存在的東西，此處僅為示例）。→ 引用路徑沒驗，弱模型會照著撞牆。

## 6. Skill 撞名裁決表（多個 skill 都像時）

優先序總則：使用者指示 > CLAUDE.md 與 docs/ops > skills > 預設行為。以下是常見撞名的裁決：

| 情境 | 用哪個 | 不用哪個 |
|---|---|---|
| 修 bug、有錯誤訊息 | `superpowers:systematic-debugging`（或 mattpocock 的 `diagnosing-bugs`，二選一，先到先得，不要兩個都走） | `tdd`（那是「開發新功能」的流程） |
| 走 `/ops-*` 派工模板中 | 模板本身（模板已內含流程裁決） | 其他 process skills 一律不再觸發 |
| 小於 10 行的顯而易見修改 | 直接改 + §5 底線驗證 | `brainstorming`（殺雞牛刀） |
| 新功能、需求模糊 | `superpowers:brainstorming` 先釐清 | 直接動手 |
| 要 commit / 宣稱完成前 | `superpowers:verification-before-completion` 與本檔 §2 並用（不衝突） | — |
| 制度檔修改 | `04-maintenance.md`（本制度） | `writing-great-skills` 等通用 skill |

## 7. 這套 rubric 的極限（誠實條款）

可外化的是**流程判斷**（何時停、何時驗、何時升級）。以下兩類補不了，遇到就明說：

- **品味判斷**（命名好不好、抽象層漂不漂亮、文案語氣）：rubric 只能給底線（一致性、無錯字），給不了「好」。處置：交給使用者或升級模型給第二意見，並明說「這是品味題，我的選擇是 X，理由 Y，可換」。
- **模糊題**（需求本身有多種合理解讀且無法從 repo/ADR 推斷）：不要選一個硬做。處置：照 §3 停下來問；使用者不在就選最保守（可逆）的解讀，並在回報開頭標明所做的解讀。
